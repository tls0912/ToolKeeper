# ConvAnvil 實作狀態

更新日期：2026-09-28。版本：0.1.0 開發預覽。

ConvAnvil 是獨立的 Windows 文字編碼、位元組轉換與 JSON 檢視工具，使用 .NET 10 與 WPF。產品規格已改名為 [`003_ConvAnvil.md`](products/003_ConvAnvil.md)。目前 0.1.0 開發預覽採 File、Text、Bytes 三個分頁，所有內容均在本機處理；JSON Viewer 已列入 003 產品範圍，尚未實作。

## 建置與執行

在 Windows 安裝 .NET 10 SDK 後，於儲存庫根目錄執行：

```powershell
dotnet restore src/ConvAnvil/ConvAnvil.csproj
dotnet build src/ConvAnvil/ConvAnvil.csproj -c Release
dotnet test tests/ConvAnvil.Tests/ConvAnvil.Tests.csproj -c Release
dotnet run --project src/ConvAnvil/ConvAnvil.csproj
```

Release 建置後可執行 `src/ConvAnvil/bin/Release/net10.0-windows/ConvAnvil.exe`；這是需要 .NET 10 Windows Desktop Runtime 的開發輸出，尚未製作安裝包或獨立執行的發行包。

從工具番本體的開發輸出啟動 ConvAnvil 時，會優先選擇與宿主相同的 Debug／Release 組態。更新共用介面後，也須建置該組態的 ConvAnvil，確保啟動目錄中的 `ToolKeeper.UI.dll` 已更新；只建置 Release 不會更新 Debug 的副本。

ConvAnvil 依[工具番介面標準](UI-STANDARD.md)使用 `AppWindow`／`WindowFrame`：關閉 Windows 原生標題列，保留工具番本體相同的竹紋頂列與視窗操作鈕；簡介和右側「風格／語言／關於」同列，預設風格為竹子亮色。File／Text／Bytes 工作區保留產品自己的功能配置。

開發環境第一次還原 NuGet 套件需要網路；應用程式的檔案檢查與轉換不需要網路、帳號或雲端服務。

## File：診斷與轉檔

1. 開啟文字檔，查看可能的編碼、BOM、換行格式與內容。
2. 如果內容與預期不符，指定來源編碼重新解碼。編碼偵測是推測，必須連同內容一起判讀。
3. 選擇目標編碼，檢查轉換結果與錯誤提示。
4. 預覽有效時另存新檔。

轉換採嚴格解碼與編碼。來源資料不符合指定編碼，或目標編碼無法表示某個字元時，會阻止轉換並顯示原因；不會默默寫成 `?` 或 Unicode 替代字元。

輸出前還會將編碼結果重新解碼、比對原文字，攔截部分舊編碼中會改變字元的對應。換行可保留原樣，或明確選擇 LF／CRLF；BOM 由所選輸出編碼控制。

目前先採另存新檔，拒絕覆寫已存在的目的檔案，也不能直接寫回來源。同目錄暫存檔完整寫入後，才以不覆寫的方式移至目的檔名。需要替換舊檔時，先檢查輸出，再自行管理檔案。

轉換使用本次開啟時讀入的內容；來源檔案之後在其他程式中修改時，需要重新開啟，才會讀入新版本。

## 編碼與偵測

目前可選擇：

| 編碼 | BOM 選項 |
| --- | --- |
| UTF-8 | 有／無 |
| UTF-16 LE、UTF-16 BE | 有／無 |
| UTF-32 LE、UTF-32 BE | 有／無 |
| Windows ANSI | 使用本機 Windows 的實際 ANSI Code Page，顯示 CP 編號 |
| Big5（CP 950）、Shift_JIS（CP 932） | 無 |
| GB18030（CP 54936）、GBK（CP 936） | 無 |
| Windows-1252、ASCII | 無 |

偵測使用 [UTF.Unknown 2.7.0](https://www.nuget.org/packages/UTF.Unknown/2.7.0)，第三方 API 集中在編碼偵測服務。優先辨識 BOM；沒有 BOM 時，使用偵測器的候選與信心值。信心值不是正確率保證；空檔案與純 ASCII 範圍內容無法唯一判斷原始編碼，會清楚說明並暫用 UTF-8。候選不在目前清單中時，也會顯示原因，讓使用者手動指定。

BOM 依最長標記優先識別，避免將 UTF-32 LE 誤認為 UTF-16 LE。解碼只移除與所選來源編碼相符的起始 BOM，不會不分編碼地刪掉開頭資料。第三方版本、來源與授權見 [套件說明](../src/ConvAnvil/THIRD-PARTY-NOTICES.md)。

## Text：檢視文字對應的位元組

輸入或貼上文字，選擇編碼與位元組格式，再按 `Text → Bytes`。可複製結果或送往 Bytes 分頁；換行操作可將 CRLF／LF／CR 正規化為 LF 或 CRLF。

字元統計使用 Unicode scalar 數量，輸入上限與錯誤位置則使用 UTF-16 單位；例如一個一般 emoji 是一個 scalar、兩個 UTF-16 單位。這不是畫面上字形的數量，組合字與多碼位 emoji 可能有多個 scalar。無效的孤立 surrogate 會單獨識別並在編碼時阻止轉換。

實際的 CR、LF、TAB、NUL 等控制字元與畫面上的可視化標記分開處理。輸入兩個字元 `\r` 不會自動變成 CR，`\n` 也不會自動變成 LF；若要轉換實際換行，應直接輸入換行或使用換行轉換操作。

控制字元檢視是唯讀診斷：實際控制碼顯示成 `⟦CR⟧` 等標記，原文反斜線顯示成 `\\`，原文的 `⟦` 前面加上反斜線，避免原文假扮控制字元標記。轉換使用原始文字，不使用這份可視化結果。

例如輸入 `ABC中文`，使用 UTF-8 的 Hex 結果為：

```text
41 42 43 E4 B8 AD E6 96 87
```

## Bytes：解析與還原文字

使用者明確選擇 Hex、Decimal 或 Binary，避免同一串數字被當成不同進位。Hex 支援常見輸入形式：

```text
41 42 43
0x41 0x42 0x43
41,42,43
\x41\x42\x43
```

Hex 每個位元組需要兩位數，Binary 需要八位 0／1，Decimal 必須是 0–255。位元組可用空白或逗號分隔；只有 `\xHH` 可以直接相連。尾端逗號、空項與不完整的數值都會報錯。

解析後按 `Bytes → Text`，依選定編碼還原文字。可選擇是否移除與解碼編碼相符的起始 BOM。格式不合法、數值超出一個位元組，或還原編碼不相容時，會顯示錯誤；不會略過有問題的輸入後繼續產生看似成功的結果。

輸入格式錯誤位置從 1 起算，以 UTF-16 單位定位；解碼失敗則顯示位元組位置與十六進位偏移。

「複製文字」複製完整解碼結果。結果含有 NUL 時會停用該按鈕並顯示原因，因為 Windows 文字剪貼簿不能保留中間的 NUL；可保留原始 Bytes 表示。空結果不清除既有剪貼簿。

## 資料量與預覽

| 項目 | 開發版上限 |
| --- | --- |
| File 開啟檔案 | 16 MiB（16,777,216 bytes） |
| Text 輸入 | 262,144 個 UTF-16 單位 |
| Bytes 輸入 | 1,048,576 個 UTF-16 單位 |
| 各內容預覽 | 前 24,000 個 UTF-16 單位，避免切開 surrogate pair |

預覽截短時顯示提示；檔案轉換仍檢查整份已載入內容，不只檢查畫面上看得見的部分。「複製」按鈕會取得完整結果，手動選取預覽區只能取得畫面中顯示的部分。超過輸入上限時不會靜默截斷後轉換，應改用 File 或分段處理；目前未實作大型檔案串流。
